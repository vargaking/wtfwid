# wtfwid — spec, version 1

"What the f was I doing." One screen that shows every ticket you have worked on,
laid out on a timeline, with the state of the Claude Code session and pull request
behind it.

Every statement has an ID and a mark:

- **stated** — the owner said it.
- **assumed** — a default picked while building. Review these first.
- **open** — undecided. Nothing is built for it yet.

Tests name the statements they cover (`S-…` in the test title). `pnpm spec` runs the tests
and lists every built statement that no test names, and every test that names a statement
this file does not have. A statement that is checked some other way says so at its end:
`{no test: why}`.

## Purpose

- **S-01** stated — It is a personal tool, not a product. Maybe open source. {no test: an intention, not a behaviour}
- **S-02** stated — The view is visual. Lists and text are what it replaces. {no test: an intention, not a behaviour}
- **S-03** stated — Version 1 only reads. It changes nothing in Linear, GitHub or Claude Code.

## The timeline

- **S-10** stated — Time runs left to right, linearly, with no fixed window. Pan to go back.
- **S-11** stated — A feature is a horizontal line. A new feature can branch off an existing line.
- **S-12** stated — Finished features stay in place on the timeline. There is no separate "closed" section.
- **S-13** assumed — Finished lines are drawn faded and folded (S-16), and one button hides them altogether.
- **S-14** assumed — The view opens scrolled to now. Zoom changes pixels per day (buttons, or ctrl/cmd + wheel). The buttons zoom around the open ticket when it is in view, the wheel around the pointer. Zoomed far enough in, the axis shows hours as well as dates.
- **S-15** assumed — The counts in the header are buttons. Each one scrolls to the next ticket in that state and opens it, going round. A "now" button scrolls back to now. Reason: with stacked rows the timeline is taller than the window, and a ticket that needs you can be off screen. The counts include **open**: started, not finished, nothing running on it. For those the side panel also says how long ago they were started.
- **S-16** assumed — A finished line is folded: a thin strip with one row of small marks and no names, so history keeps its place without taking the room. Clicking the line's name unfolds it; clicking again folds it. Reason: with stacked rows (S-35) a line is as tall as its busiest moment, and most lines are finished.
- **S-17** assumed — A search box in the header finds tickets by ID, number or words in the title; `/` puts the cursor in it. Choosing a result scrolls to the ticket and opens it. If its line is finished and folded or hidden, the line is shown in full for as long as that ticket is open, and goes back to how it was afterwards: looking something up does not change what you chose to hide or fold. The same holds for a ticket opened from the Related list (S-86) or from a day (S-89).
- **S-18** assumed — wtfwid sends a desktop notification when a ticket starts needing you, when a session fails, and when a session that was working stops. Clicking it shows the ticket. A button in the header turns this on and off; it starts on where notifications are already allowed (the desktop app) and off in a browser until you allow them. The number of tickets that need you is also in the window title. To notice quickly, the screen asks every 15 seconds whether any local session changed state, and reads everything again at once if one did. Answers from Linear and GitHub are reused for 45 seconds, so those quick refreshes only read the sessions again. A refresh where Linear or Claude Code could not be read is not compared with anything: tickets missing for a moment are not news.
- **S-87** assumed — `node scripts/status.js` prints one line for a status bar or a shell prompt: how many Claude Code sessions need you and how many are working (`2 need you · 3 working`, or `idle`). Reason: the question asked most often is whether a session is waiting, and a bar answers it all the time without opening anything. It asks only `claude agents`, so it needs no Linear key, no server and no window, and it counts sessions, not tickets. A session needs you when it is blocked or waiting for input, the rule S-40 uses. `--json` prints the counts and the sessions that are running. `--waybar` prints a line for a Waybar module: the number that need you, the sessions in the tooltip, and a class to colour it by. `--watch` keeps running and prints only when the answer changed; like S-85 it asks `claude agents` only when Claude Code's own session files change, and four times a minute regardless. When `claude` cannot be run, the text form prints nothing and fails, and the Waybar form says why in its tooltip. It runs from a checkout with Node; it is not in the packaged app.
- **S-19** assumed — With nothing selected, the side panel lists what is unfinished: most urgent first, then longest open first, each with its state and how long it has been going. Clicking one shows it on the timeline. Escape, or the back button on a ticket, returns to the list. Reason: it is the short answer to the question the tool is named after, in a place that was otherwise empty.
- **S-80** assumed — Under the timeline is an overview strip: all of time, from the first ticket to now, squeezed into the width of the timeline. Reason: the timeline opens at now and history scrolls off to the left, with nothing to show how much there is, where the busy weeks were, or where in it you are. A bar says how many tickets started in that stretch of time: a few hours while history is short, days or weeks as it grows. Its height follows the square root of the count, so one ticket can still be seen next to twenty. Finished work is dim. If anything in a bar is unfinished, the foot of the bar, at least half of it, has the colour of its most urgent state, so loose ends show wherever they sit in history. A window marks the part of time the timeline is showing; it follows scrolling and zooming and is never drawn narrower than 14 pixels. Clicking the strip brings that time to the middle of the timeline, dragging pans. There is a mark for now, and a few dates: days, Mondays, months or years, whichever fit. The strip counts the lines the timeline shows, so with "Hide finished" on the hidden ones are left out. The bars do not move when the timeline is zoomed, so a busy week stays where you remember it. For the keyboard and screen readers the strip is the timeline's scrollbar: arrow keys pan by a step, Page Up and Page Down by nearly a screenful, Home goes to the start, End to now. When the whole timeline fits in the window the strip stays, with the window over all of it: it is still the one place that shows how much happened when, and a strip that came and went would make the screen jump while zooming.

## What a line is

Based on how the Linear workspace this was built for is organised: a few hundred issues in
three weeks, grouped into projects and project milestones, no sub-issues.

- **S-20** assumed — Each Linear project is a trunk line. It carries the project's issues that have no milestone.
- **S-21** assumed — Each project milestone is a line that branches off its project's trunk at the time of its first activity.
- **S-22** assumed — Issues with no project go on a "No project" trunk.
- **S-23** assumed — Within a project, milestone lines are ordered newest first under the trunk, so branch connectors never cross another line.
- **S-24** open — A branch that starts from one specific session or ticket (stated: "from a voice chat line we branch off LiveKit setup, screen share"). Linear has no field for this today. Candidates: sub-issues, or an issue relation. Checked on real data: none of the 250 most recent issues has a parent, so sub-issues give nothing to draw. What is built instead is S-86: a session that moves from one ticket's branch to another's relates the two, and the line between them is drawn when either is open. It is not drawn as a branch of the timeline, because how often sessions really move is not known yet; "Check connections" (S-79) counts it.

## What a node is

- **S-30** assumed — A node is one ticket (Linear issue). Its session and pull request are shown on the node, not as separate nodes. Reason: in the real data, ticket, session and pull request are close to one-to-one, and three nodes per ticket would triple the density.
- **S-31** assumed — The shape shows how far the ticket got: circle = ticket only, square = has a Claude Code session, diamond = has a pull request.
- **S-32** assumed — A ticket appears once it has been started or completed, or has a session or pull request. Untouched backlog is not shown.
- **S-33** assumed — Cancelled and duplicate issues are not shown.
- **S-34** assumed — A node sits at the time work began: issue `startedAt`, else first session, else first pull request, else completion.
- **S-35** assumed — Tickets started close together stack in rows under their line, in the order they started, and the lane grows to fit. Reason: in the real data tickets start in bursts, so on one row most of them merged into counted clusters at every zoom. A mark never moves off its own time and never overlaps another. When rows get crowded, names give way first: a ticket goes where its mark has room and the name before it is cut short. Only when every one of the five rows has a mark in the way does a ticket merge into the nearest one in time, which becomes a counted cluster, coloured by its most urgent member. A cluster's pill starts at its first ticket and reaches right.
- **S-36** assumed — A ticket still in play is drawn full size with its ID and title next to it, as much of them as fits before the next ticket in its row. A finished one is a small mark, with its ID or title in a dimmer colour under the same rule. A session that ended without a ticket is history too, whatever state it ended in. Every node has its full name as a tooltip.

## State

One state per ticket, the first of these that applies:

- **S-40** assumed — **needs you**: a live session on it is blocked or waiting for input.
- **S-41** assumed — **failed**: its most recent session failed and the issue is not completed.
- **S-42** assumed — **working**: a live session on it is busy.
- **S-43** assumed — **done**: the issue is completed.
- **S-44** assumed — **ready for review**: the issue's status name contains "review", or it has an open, non-draft pull request.
- **S-45** assumed — **open**: anything else.

## Linking

- **S-50** assumed — A session belongs to a ticket when its name, the git branch it is on, or its working directory contains the issue's branch name or its identifier (`ENG-123`, any case). The branch is read from the end of the session's transcript on every refresh, so a session does not have to be named after its ticket.
- **S-51** assumed — A pull request belongs to a ticket when its branch or title does.
- **S-52** assumed — Sessions that match no ticket go on an "Unsorted" line, so nothing running is hidden. Open pull requests that match no ticket go there too.
- **S-53** assumed — Claude Code only lists sessions that still exist. wtfwid remembers every session it has seen in `~/.wtfwid/sessions.json`. A remembered session that is no longer listed keeps its place; if it was working or waiting it becomes "open".
- **S-54** open — Planning chats on claude.ai. Nothing outside claude.ai can list them, so the link has to be written from inside the chat. Built as far as that goes: with the connector (S-91) a chat can leave a note on a ticket, which is then on the timeline. Still open: the chat does not know its own address, so the note links back only if you paste the link in; and the chat has to be asked to note it, or told to in the project's instructions.
- **S-55** assumed — Opening a ticket shows, for each of its sessions: what it was started with, the last thing you asked, the last thing Claude said, and the pull requests it opened. This is read from Claude Code's own transcript of the session (`~/.claude/projects/…/<session id>.jsonl`) at the moment the ticket is opened. Nothing is written and no model is called. Reason: Claude's last message usually already says what was done and what is left. The transcript is not a documented format (checked against Claude Code 2.1.296), so a line that is not understood is skipped, and a transcript that is gone shows nothing.
- **S-56** assumed — Tickets are also related through the files their pull requests change, as GitHub lists them. This is the same relation as S-86, from another source: it needs no session on this machine, and it sees every change, however it was made. Each pull request on the timeline costs two more requests (its files, its commits). They are made once, again only when GitHub says the pull request changed, most recently changed first, eighty pull requests a round, for about a second before the screen is answered and the rest afterwards; the answers are kept in `~/.wtfwid/pulls.json`, readable only by you. A pull request that could not be read is left alone for half an hour, and when GitHub says to slow down nothing is asked for a quarter of an hour. Without a GitHub token nothing of this is read: GitHub allows sixty requests an hour then, which the first round would use up. A file in a repository on GitHub and the same file in a folder on this machine count as two files, because nothing says they are the same.
- **S-57** assumed — Context pack: an unfinished ticket has a button that copies a prompt for a new session. It holds what wtfwid knows: the ticket's ID, status and link, the branch and folder, its pull requests, and for each earlier session what it was started with, the last thing asked and how it ended. It does not copy the ticket's own text; the new session reads that from Linear. It also names the related tickets (S-86) and the files they share, so the new session knows where else to look.
- **S-58** open — A written "decided / still open" summary per session. Not built as a hook that runs a model over the transcript: that costs tokens on every session. Two things get most of it for nothing: S-55 and S-91 show the last thing Claude said, which is usually that summary; and with the connector (S-91) a session or chat can be asked to write one itself, as a note with "decided" and "still open".
- **S-59** assumed — A session whose transcript is still on the machine has a button that copies the command to resume it: `cd <its folder> && claude --resume <its id>`. wtfwid copies; it does not run anything. For a Windows folder the command is written for PowerShell (`cd '…'; claude --resume …`); that form has not been run on Windows.
- **S-83** assumed — wtfwid also finds past sessions on disk. Claude Code keeps a transcript of every session for a few weeks; each one is a session, with its folder, start, name, branch and last sign of life read from the first and last lines of the file. So the timeline has history the first time the app is opened, not only from then on. A found session is drawn on the ticket it belongs to. One that belongs to no ticket is left out: it is another project's. Found sessions are remembered like the others (S-53), so they outlive their transcripts.
- **S-84** assumed — For each session the side panel says what it did: how long it was at it (pauses over five minutes left out), how many prompts and commands, which files it edited and which of those it made, roughly how many lines it wrote and replaced, the tokens it used and what Claude Code says it cost. All of it read from the transcript. It only sees edits made with Claude Code's edit tools; a file changed by a shell command is not counted. What the session's sub-agents did counts as the session's: Claude Code keeps their transcripts beside the session's own, and their edits, commands, tokens and time are added in. Waiting for a command or a sub-agent to come back counts as being at it, up to an hour, so a tool left waiting for your permission overnight is not a night of work. The cost is added up over every run of a resumed session. The files a session changed most go into the context for a new session (S-57).
- **S-85** assumed — While a window is open, wtfwid follows the sessions that are running and shows what each is doing as it happens: the command it runs, the file it edits, the first line of what it says, what you typed. The side panel has a live feed per running session, the list of unfinished work shows each one's latest action, and a ticket with something running on it breathes on the timeline. It works by reading only what was added to each running session's transcript, once a second, and sending it to the window over one open connection. While a session waits for its sub-agents, the feed shows what they are doing. The same connection says at once when a session starts, stops or changes state, so the screen and the notifications (S-18) no longer wait for the next check. To learn that, wtfwid asks `claude agents` only when Claude Code's own session files change, and four times a minute regardless.
- **S-86** assumed — wtfwid works out which tickets belong together, from what their sessions did. Two tickets are related when their sessions changed the same files; a file counts for less the more other tickets changed it too, a file that more than a handful of tickets changed (six, up to twelve when there are many tickets) counts for nothing, as does any lock file, and a file outside the checkout never counts. Sessions on different tickets usually run in a worktree each, so a path is compared without its worktree and from the top of the checkout (the nearest folder above the session's that holds `.git`); the same path in two different checkouts is two files. Two tickets are also related when a session went from one's branch to the other's: the second grew out of the first. The same is read from pull requests (S-56, S-90), so it works for sessions that ran in the cloud. Opening a ticket draws a line from it to each of its strongest relations (at most six): solid with an arrow the way a session went, dotted for shared files, thicker the more they share. The lines run under the names and the line titles, so they never strike through text. Finished work that is not related steps back; what is still in play keeps its full colour, because a ticket that needs you must not fade while you read another. The side panel lists the same tickets with the reason and the shared files, and clicking one goes there. A session with no ticket that began on a ticket's branch is related to that ticket the same way, which is a hint where it belongs. To know all this, each session's transcript is read when it is new or has changed (a running one at most every two minutes; every file of a session that changed folder), newest first, for about a second per refresh and the rest in the background; what was learned is kept in `~/.wtfwid/index.json`, readable only by you, so relations outlive the transcripts Claude Code deletes. Claude Code also rewrites a transcript shorter when it compacts a long conversation; reading it again never drops what an earlier reading found, but what was compacted away before wtfwid first read a session is not known. It only sees edits made with Claude Code's edit tools.
- **S-88** assumed — The side panel says how much work went into a ticket: the time its sessions were at it (pauses over five minutes left out), over how many sessions, and what Claude Code says they cost; and from its pull requests, how many commits and how many lines added and removed. While a ticket is open, the stretches of time it was worked on are drawn along the bottom of the time axis, so you can see when it happened and how it was spread. These totals come from what wtfwid has kept of each session (S-86), so they stay whole after a transcript is compacted or deleted; the detail per session (S-84) shows what its transcript holds now.
- **S-89** assumed — The dates on the time axis are buttons. Clicking one shows that day in the side panel: how much session time there was, for how much of the day something was running (sessions side by side each count as session time, once as time of the day, also when they are on the same ticket), roughly what it cost, and the tickets worked on, most first, each with its time as a bar, along with the ones that were only started or completed that day (twelve listed, the rest behind "show all"). For a day with no session time the headline is how many tickets were started and completed. When the axis has room for one date a week, a date stands for its week. "now" is today. The day is marked on the timeline by two lines; clicking the date again, or Escape, lets go of it. With the keyboard, Tab stops at "now" and the arrow keys go from date to date, so the dates are not in the way of everything behind them. Above the list of unfinished work one line says how much was done today and opens the day. A ticket's cost is counted by the share of its work that fell in the day, so it is an estimate. Work that ran over midnight belongs to both days.
- **S-90** stated — Most of the owner's sessions run in the cloud (Claude Code on the web), not on the machine wtfwid runs on. Assumed: nothing outside claude.ai can list those sessions or read their state (checked against the Claude Code documentation, October 2026), and they leave no transcript here. What they do leave is their link, `https://claude.ai/code/session_…`: in the description of the pull request they open and as a `Claude-Session:` trailer on every commit they make. wtfwid reads both. A ticket whose pull request names a session shows it as a cloud session with a button that opens it on claude.ai. One cloud session often works on several tickets; the tickets whose pull requests carry the same link are that session's way, in the order they were started, and opening one of them draws the whole way on the timeline (solid lines with arrows, lighter away from the open ticket) and lists the tickets just before and after it. For work done in the cloud the side panel counts what the pull requests hold: commits, and lines added and removed as GitHub counts them; the commits' times are drawn on the time axis; and a day (S-89) lists the tickets that had commits that day. Not known for a cloud session, and not shown: whether it is running or waiting for you, how long it worked, what it cost, and what was said in it. Checked on the two real repositories this was built for: about nine pull requests in ten carry a session link, and about nine in ten name their ticket. "Check connections" (S-79) says how many do, and no longer calls it a fault when there are no transcripts on this machine.
- **S-91** stated — "We can make a connector that agents can call." Assumed, all of it: a relay, a very small server of your own on the public internet (the `relay` folder: a Cloudflare Worker with a D1 database, or the same code under Node), that sessions write to and wtfwid reads from. It exists because wtfwid runs on localhost, which a session in the cloud cannot reach, and because nothing can ask a cloud session how it is doing: it has to say so itself. Three things talk to it, with two tokens: a write token for sessions and the connector, a read token for wtfwid.
  - **A hook** (`relay/hook.sh`, with the block in `relay/settings.example.json`), committed to a repository, reports the session's events: a prompt means working, a permission question means it needs you, the end of its turn means it is your move, and what it said last is kept with that. It sends the session's cloud id, its git branch and its repository, so the session lands on its ticket the same way a local one does (S-50). It does nothing unless two environment variables are set, so it is safe in a public repository; it runs in the background and always exits 0, so it cannot hold a session up or fail it. Sitting at the prompt after a finished turn is not "needs you", the same as for local sessions (S-40).
  - **A connector** (Model Context Protocol, at `/mcp`) with three tools: leave a note on a ticket (title, summary, what was decided, what is open), say which ticket a session is for, and read back what is noted on a ticket. Claude Code sends the write token as a header. A connector added on claude.ai cannot send one, so there the token is the last part of the address, and that address is the secret.
  - **wtfwid** reads `/state` with the read token: at most every five seconds while a window is open, and with every refresh. A cloud session that reports is a session like any other: it gives its ticket its state, counts in the header, raises the notifications (S-18), and its panel says what you last asked, what it last said and when it was last heard from, with a button to its page. A session that said "working" and then nothing for three hours is no longer believed. Notes show on their ticket, newest first, and go into the context for a new session (S-57). The relay's address and read token are in Settings; the address must be https (plain http only for one on this machine). When the relay cannot be reached the screen says so, and that refresh is not compared with anything, so it raises no notifications.
  - The relay keeps the latest state of each session and the notes for six weeks, and nothing else: no transcripts, no tickets, no keys. It stores up to 400 characters of your last prompt and 1,200 of Claude's last reply per session; that is the price of seeing what a session is waiting for.
  - Not done here and yours to do: deploying the relay, setting the two variables in the cloud environment, allowing the relay's domain there, and committing the hook to each repository. A cloud session that has several repositories does not run repository hooks at all (Claude Code's rule), so it reports nothing. Checked: the relay's code in Cloudflare's own local runtime with a real D1 database and under Node; the hook script against both; the connector with Claude Code's own client; and one made-up cloud session end to end, from hook to notification on screen in about five seconds. Not checked: a deployed relay, a real cloud session's hooks, and the connector from a claude.ai chat.

## Desktop app and settings

- **S-70** stated — It runs as a desktop app (Electron). The same screen still runs in a browser with `pnpm dev`. {no test: checked by running the desktop app}
- **S-71** stated — Keys and other settings are entered in a settings dialog. They are kept in `~/.wtfwid/settings.json`, readable only by the user.
- **S-72** assumed — The desktop app encrypts keys with the operating system's keychain. Where there is no keychain, and in the browser version, keys are stored without encryption and the dialog says so. A key the desktop app encrypted shows as unreadable in the browser version.
- **S-73** assumed — Saved settings win. Anything not saved falls back to `.env` and the environment.
- **S-74** assumed — A saved key is never sent back to the screen. The dialog can replace it or remove it, not show it.
- **S-75** assumed — Only you can reach it. It answers only requests addressed to this machine, and the desktop app also requires a one-off token that only its own window has.
- **S-76** assumed — Links to Linear and GitHub open in your browser, not inside the app. {no test: checked by running the desktop app}
- **S-77** assumed — The desktop app takes `PATH` from a login shell, so it finds `claude` and `gh` when started from a launcher. {no test: checked by running the desktop app}
- **S-78** assumed — The zoom, the "Hide finished" choice and which finished lines are unfolded are remembered on this machine, so the view comes back the way it was left. Stored in the window's own storage, not in the settings file. For that storage to survive a restart, the desktop app serves itself on the same local port every time (47113), and takes any free one if that is in use.
- **S-79** assumed — Settings has a "Check connections" button. It tries each source for real with the saved settings and says what came back: how many Linear issues, how many pull requests per repository, how many Claude Code sessions, whether their transcripts can be read, and how many sessions end up on a ticket. It shows counts only, never a title or what a session said, so the result can be pasted anywhere.
- **S-81** assumed — The desktop app puts an icon in the tray. Its menu has "Show wtfwid", a line that says how many tickets need you and shows the window too, a checkbox "Keep running when the window is closed", and "Quit". The icon has an amber dot while something needs you. The count is read from the window title (S-18), and is also set as the app's badge where the system shows one. "Keep running" is off until you tick it. With it on, closing the window hides it instead of quitting, so the page stays alive and its notifications (S-18) keep coming; "Quit" in the tray menu and Ctrl+Q or Cmd+Q still really quit. The choice is kept in `~/.wtfwid/desktop.json`, readable only by the user. A desktop without a tray (plain GNOME) never shows the icon, and the app cannot tell. So nothing depends on the tray: the app starts the same without one, and starting wtfwid again always shows the window of the one that is running. The menu, the hiding and the second start were checked by running the built app on a virtual display; the icon has not been seen in a real tray, and none of it has been run on Windows or macOS.
- **S-82** assumed — wtfwid says when a newer version is out. It asks GitHub's public API for the latest release of its own repository: one request, with no key and no token, when it starts and every 6 hours after that. The answer is reused for those 6 hours, and a try that failed is not repeated for 30 minutes. Being offline or rate-limited is not an error and shows nothing. `WTFWID_NO_UPDATE_CHECK=1` turns the check off. When there is a newer version, the header shows a link to its release page ("v0.1.2 is out"). Where the app runs from a Linux AppImage it is a button instead ("Update to v0.1.2"): it downloads the new AppImage next to the old one, checks its size and its SHA-256 against what GitHub published, and moves it over the old file in one step. If anything does not match, or GitHub published no checksum for the file, the download is deleted, the old file is left as it was, and the header says what failed and goes back to the link. The download only ever comes from the release files of this repository. The file keeps its name, old version number and all, so a launcher or desktop entry that points at it keeps working. After that the button says "Restart to finish". wtfwid never restarts by itself: sessions may be running, and you may be reading. The Windows and macOS builds are not code-signed and cannot replace themselves safely, so there, in the browser version and when run from source it stays a link. Nothing of this is shown in demo mode. Replacing and restarting was run with a real AppImage against a stand-in for GitHub; GitHub itself was not reachable from the machine it was built on.
